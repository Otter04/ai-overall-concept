## 장 도입

7장의 앱은 정해진 순서대로 일했습니다. 원문을 가져오고, 근거를 고르고, 지침과 함께 입력을 묶어 모델을 한 번 실행했습니다. 그런데 7장 끝에서 이런 질문을 남겼습니다. 그 지침은 누가, 어떤 모양으로 준비해 둘까요? 일이 여러 단계로 늘어나면 앱은 모델과 도구를 몇 번, 어떤 순서로 부를까요?

이 장은 1.5에서 소개만 했던 **Skill**을 실제 문장으로 열어 봅니다. 개발자가 Skill에 무엇을 적는지(8.2), 그 문장들이 어떤 행동으로 이어지는지(8.3~8.4)를 본 뒤, 마지막으로 같은 작업을 Skill 없이 한 결과와 Skill을 적용한 결과를 **실제로 실행한 출력**으로 나란히 비교합니다(8.5).

---

## 8.1 Skill의 역할과 도구와의 관계

1.5에서 Skill은 특정 작업의 절차, 기준, 참고자료, 결과물 형식, 검증 방법을 묶어 둔 작업 안내서라고 했습니다. 1장의 비유로는 업무 매뉴얼입니다. 그리고 그림 1-8에서 본 것처럼, Skill은 모델 입력에 들어가 출력의 방향을 정할 뿐이고 실제 기능은 앱이 도구로 실행합니다. 이 관계는 이 장에서도 그대로입니다.

이 절에서 새로 볼 것은 **앱이 Skill을 언제 입력에 넣는가**입니다. 앱에 Skill이 여러 개 있다고 해서 매번 모두 넣으면 입력이 길어집니다. 2.2의 컨텍스트 윈도와 7.3의 입력 길이 조절에서 본 것과 같은 문제입니다. 그래서 공개된 Skill 규격에서는 단계를 나누어 넣습니다.

| 단계 | 입력에 들어가는 것 | 언제 |
|---|---|---|
| 1 | 모든 Skill의 이름과 짧은 설명 | 처음부터 |
| 2 | 지금 작업에 맞는 Skill의 본문(작업 안내) | 요청이 그 설명과 맞을 때 |
| 3 | 그 Skill에 딸린 참고 파일이나 스크립트의 결과 | 본문을 따라 작업하다 필요할 때 |

이 표는 공개 규격인 Agent Skills 명세와 Anthropic의 Claude 문서에 적힌 방식을 정리한 것입니다.<!-- 출처 확인 2026-11-03: https://agentskills.io/specification (Progressive disclosure 절), https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview (Level 1~3) --> 설명은 처음부터 들어가므로, 설명에 **무슨 일을 하고 언제 쓰는지**를 잘 적어 두어야 앱이 알맞은 Skill을 고를 수 있습니다. 요청이 두 Skill의 설명과 함께 맞으면 둘을 같이 넣을 수도 있고, 맞는 Skill이 없으면 Skill 없이 앱의 기본 지침만으로 실행됩니다. 설명과 요청이 맞는지 보는 방법과 Skill을 넣는 방식은 제품마다 다릅니다.

7장의 지침과 Skill의 관계도 여기서 정리됩니다. 7.4의 지침 둘째 줄("자료에 없는 내용은 추측하지 말고 확인이 필요하다고 적는다")은 앱의 지침 한 줄이었습니다. 이런 문장을 한 작업에 필요한 만큼 모아 이름과 설명을 붙이고, 필요할 때만 입력에 넣게 만든 것이 Skill입니다.

> **이해 확인**
> 8.1 표의 방식을 쓰는 앱에 Skill이 스무 개 있습니다. 직원이 교육 안내문 검토를 요청했을 때, 스무 개 Skill의 본문이 모두 입력에 들어갈까요?

## 8.2 개발자는 Skill에 무엇을 적는가

Skill에 적는 내용은 다섯 가지로 나누어 볼 수 있습니다. 공개 규격에서 Skill은 폴더 하나이고, 그 안에 작업 안내 파일(SKILL.md)이 반드시 있으며, 참고 파일이나 스크립트는 필요할 때 함께 둡니다.<!-- 출처: agentskills.io/specification의 Directory structure (SKILL.md 필수, scripts/·references/·assets/ 선택) -->

| 적는 것 | 예 | 어디에 적나 |
|---|---|---|
| 목적과 사용 조건 | "교육 안내문을 검토하고 보고서로 정리할 때 사용한다" | 작업 안내 파일 맨 위의 설명(description) |
| 필요한 입력과 작업 순서 | 안내문에서 무엇을 찾고 어떤 순서로 정리할지 | 작업 안내 파일 본문 |
| 사용할 도구와 참고자료 | 파일 읽기 도구를 쓸 것, 보고서 양식 파일 | 본문, 참고 파일 |
| 결과물 형식 | 보고서의 항목 순서 | 본문, 양식 파일 |
| 예외 처리와 검증 기준 | 자료에 없는 항목의 표시 방법, 작성 뒤 대조 | 본문, 검증 스크립트 |

'사용할 도구'를 Skill에 적어도, 그 도구를 쓸 수 있는지는 Skill이 정하지 않습니다. 어떤 도구를 연결하고 어떤 권한을 줄지는 앱이 따로 관리합니다. 7.4에서 권한 없는 자료를 지침이 아니라 검색과 조회 단계에서 막은 것과 같은 원칙입니다.

Skill에 든 스크립트도 Skill이 스스로 실행하는 것은 아닙니다. 모델의 요청을 받은 앱이 스크립트를 실행하는 도구로 스크립트를 돌리고, 그 결과만 입력에 들어갑니다. 1장 정리 표에서 Skill은 스스로 실행되거나 모델 자체를 바꾸지 않는다고 한 것이 여기서도 그대로입니다.<!-- 출처: platform.claude.com Agent Skills overview, Level 3: scripts run through bash, only their output enters context -->

그래서 스크립트가 든 Skill에는 한 가지 주의할 점이 있습니다. 스크립트는 실제로 실행되는 프로그램이므로, 처음 보는 곳에서 받은 Skill은 프로그램을 설치하는 것처럼 조심해야 합니다. Anthropic의 문서도 직접 만들었거나 믿을 수 있는 곳에서 받은 Skill만 쓰고, 그렇지 않으면 사용 전에 꼼꼼히 살펴보라고 권합니다.<!-- 출처: platform.claude.com/docs/en/agents-and-tools/agent-skills/overview Security considerations, 2026-11-03 확인 -->

> **이해 확인**
> Skill 본문에 "파일 읽기 도구로 안내문을 연다"고 적었는데, 앱에 파일 읽기 도구가 연결되어 있지 않습니다. 이 Skill을 넣으면 안내문 파일이 열릴까요?

## 8.3 Skill 작성 예시를 문장별로 읽어보기

먼저 실제 공개 규격의 모양을 짧게 보겠습니다. 작업 안내 파일은 맨 위에 이름(name)과 설명(description)을 적고, 그 아래에 작업 안내를 씁니다. 규격 문서의 예시는 이렇게 시작합니다.

```text
[실제 사례] 공개 규격 문서의 예시 머리 부분 (agentskills.io/specification)
---
name: pdf-processing
description: Extract PDF text, fill forms, merge files. Use when handling PDFs.
---
```

이름은 영문 소문자, 숫자, 하이픈만 쓰고 64자를 넘지 않게 정해져 있습니다. 설명은 무엇을 하는지와 언제 쓰는지를 함께 적도록 권합니다.<!-- 출처: agentskills.io/specification의 name·description 필드 규칙, 2026-11-03 확인 -->

아래는 이 책에서 설명을 위해 만든 Skill입니다. 실제 공개 프로젝트에서 가져온 문장이 아닙니다. 형식만 위의 규격을 따랐고, 본문은 1.5에서 보고서 작업에 필요하다고 든 기준 네 줄과, 1.5 표의 예시 "날짜는 원문과 다시 대조한다"를 합쳐 다섯 문장으로 다시 적은 것입니다. 8.5의 실험 B에는 이 내용이 그대로 들어갔습니다.

```text
[설명용 예시] 교육 안내문 검토 Skill
---
name: notice-review
description: 교육 안내문을 검토하고 보고서로 정리할 때 사용한다.
---
- 안내문에서 신청 대상, 마감일, 교육일, 예외 조건을 추출한다.
- 날짜가 서로 다르면 문서의 버전과 적용 대상을 확인한다.
- 자료에 없는 항목은 추측하지 않고 ‘확인 필요’로 표시한다.
- 보고서는 대상·일정·예외·출처 순서로 작성한다.
- 작성 후 날짜와 대상 조건을 원문과 다시 대조한다.
```

이 장에서는 다섯 문장을 차례로 S1~S5라고 부르겠습니다. 다섯 문장은 각각 다른 일을 맡습니다. 그림 8-1은 각 문장이 출력의 어느 부분에 영향을 주도록 쓴 것인지와, 앞 장의 어느 내용과 이어지는지를 정리한 것입니다.

<!-- 그림 시작: fig-08-01 -->
> **[그림 8-1] Skill의 문장과 그 문장이 이끄는 행동**
>
> - **보여줄 핵심:** Skill의 문장 하나하나는 출력의 서로 다른 부분(무엇을 찾을지, 다를 때 무엇을 볼지, 없을 때 어떻게 적을지, 어떤 순서로 쓸지, 쓴 뒤 무엇을 할지)을 겨냥한다.
> - **구성 요소:** 왼쪽에 Skill 문장 S1~S5 카드, 가운데에 '이끄는 행동', 오른쪽에 '이어지는 앞 장'. 문장 카드와 행동 사이에 화살표.
> - **배치와 흐름:** 위에서 아래로 문장 순서. S5는 '출력 안의 대조'와 '앱의 대조'로 갈라지는 표시(8.4).
> - **대체 텍스트:** 교육 안내문 검토 Skill의 다섯 문장이 각각 찾을 항목 정하기, 날짜가 다를 때 버전과 적용 대상 보기, 자료에 없는 항목을 확인 필요로 적기, 보고서 순서 정하기, 작성 뒤 원문과 대조하기로 이어지고, 각각 4장·6장·7장의 내용과 연결되는 대응표.
> - **성격:** 설명용 예시.

```text
[설명용 예시] Skill 문장과 이끄는 행동
  문장                                      이끄는 행동                               이어지는 앞 장
  S1 신청 대상·마감일·교육일·예외 조건 추출     출력에 넣을 항목을 정함                     4.3 일반 규칙과 예외
  S2 날짜가 다르면 버전과 적용 대상 확인         날짜가 여러 개일 때 볼 정보를 정함            6.9 버전 정리, 7.6 충돌
  S3 자료에 없으면 '확인 필요'                  빈 항목을 채우지 않고 표시함                 4.7·7.4 지침
  S4 대상·일정·예외·출처 순서                   결과물의 형식을 정함                        7.5 출처 번호
  S5 작성 후 원문과 다시 대조                   출력 안에 대조 결과를 적게 함 (8.4)           7.7 검증
```

<!-- 그림 끝: fig-08-01 -->

S2는 날짜가 다를 때 **무엇을 확인할지**만 정하고, 어느 날짜가 맞는지는 적지 않습니다. 확인할 것은 두 가지입니다. 같은 항목의 날짜가 문서마다 다르면 문서의 버전을 보고, 한 문서 안에 날짜가 여러 개면 각 날짜의 적용 대상을 봅니다. 8.5.2에서 다루겠지만, Skill에는 정답을 적지 않고 절차만 적어야 다른 안내문에도 쓸 수 있습니다. S3은 7.4 지침의 한 줄과 같은 뜻입니다. S5는 조금 특별합니다. 이 문장대로 출력에 "다시 대조했다"는 말이 나와도, 그것은 모델이 만든 출력의 한 부분입니다. 4.8에서 화면의 풀이가 내부 계산의 기록이 아니라고 한 것처럼, 대조했다는 문장이 곧 대조가 실제로 이루어졌다는 증거는 아닙니다. 8.4에서는 이 대조를 프로그램으로 하는 방법을 봅니다.

> **이해 확인**
> 누군가 S2를 "날짜가 서로 다르면 10월 5일을 쓴다"로 바꾸자고 제안했습니다. 이렇게 바꾸면 어떤 문제가 생길까요?

## 8.4 Skill의 지침이 실행으로 이어지는 과정

이제 이 Skill이 들어간 요청 하나를 따라가 보겠습니다. 직원이 "교육 A 안내문을 검토해서 정리해 줘"라고 요청했고, 안내문은 회사 문서함에 파일로 있다고 합니다. 1.6과 같은 상황이므로 단계표를 다시 만들지 않고, **Skill의 각 문장이 어디에서 작동하는지**만 표시합니다.

<!-- 그림 시작: fig-08-02 -->
> **[그림 8-2] Skill의 문장이 실행의 각 단계에서 작동하는 자리**
>
> - **보여줄 핵심:** Skill은 ②에서 도구 목록과 함께 입력에 들어가고, 그 뒤의 모든 모델 실행에 함께 실린다. 도구는 앱이 실행하고, S5의 대조는 모델의 출력 안에서 일어날 수도 있고 앱의 프로그램으로 따로 할 수도 있다.
> - **구성 요소:** 세로 레인(사용자 / 앱 / 모델 / 도구) 네 줄, 단계 ①~⑦, 단계 옆에 그 단계에서 작동하는 Skill 문장 배지(S1~S5). ⑥ 옆에 점선 상자 '앱이 따로 대조하는 경우'.
> - **배치와 흐름:** 위에서 아래로 시간 순서. 1장 그림 1-9, 4장 그림 4-5와 같은 레인 배치와 아이콘.
> - **디자인 메모(시안, 확정 아님):** 이 장의 대표 그림 후보다. Skill 문장 배지는 그림 8-1의 카드 색과 맞춘다.
> - **대체 텍스트:** 사용자의 요청을 받은 앱이 요청과 맞는 Skill을 골라 그 본문과 쓸 수 있는 도구 목록을 입력에 넣어 모델을 부르면, 모델의 첫 실행이 파일 읽기 요청을 출력한다. 앱이 파일 읽기 도구를 실행해 안내문 글을 입력에 더하고 모델을 다시 부르면, 두 번째 실행이 Skill의 순서대로 보고서를 출력한다. 앱이 보고서의 날짜를 원문과 프로그램으로 따로 대조하는 단계는 선택 사항으로 점선으로 표시되어 있다.
> - **성격:** 설명용 흐름도. 실제 서비스의 단계는 제품마다 다르다.

```text
[설명용 예시] Skill이 들어간 요청의 흐름 (괄호 안은 작동하는 Skill 문장)
 사용자        앱                               모델                  도구
   │─요청──────▶│ ① 요청 접수                       │                     │
   │            │ ② Skill 본문+도구 목록을 입력에 ──▶│ 1번째 실행          │
   │            │◀── ③ 파일 읽기 요청 출력 ─────────│ (S1: 안내문 필요)    │
   │            │ ④ 파일 읽기 실행 ──────────────────────────────────────▶│
   │            │◀──────────────────────────────────────── 안내문 글 ─────│
   │            │ ⑤ 처음 입력+파일 읽기 요청+안내문 ▶│ 2번째 실행          │
   │            │◀── ⑥ 보고서 출력 ─────────────────│ (S1~S5)             │
   │            │ ┈ (선택) 보고서 날짜를 원문과 프로그램으로 대조 ┈        │
   │◀─⑦ 표시────│                                  │                     │
```

각 문장이 작동하는 자리는 다음과 같습니다.

- **Skill 전체는 ②에서 입력에 들어갑니다.** 1.6의 ②처럼 쓸 수 있는 도구 목록도 함께 들어가므로, 모델의 출력이 파일 읽기 도구를 요청할 수 있습니다. ⑤에서 모델을 다시 부를 때도 앱은 처음 입력을 다시 담으므로(1.6, 4.7), Skill은 두 실행 모두에 실립니다.
- **S1은 ③을 이끕니다.** 안내문에서 항목을 추출하라는 문장이 있는데 입력에 안내문이 없으므로, 첫 실행은 파일 읽기 요청을 출력합니다. 파일을 실제로 여는 것은 ④의 앱과 도구입니다.
- **S1~S4는 ⑥의 보고서 모양을 정합니다.** 무엇을 찾을지(S1), 날짜가 여러 개일 때 무엇을 볼지(S2), 빈 항목을 어떻게 적을지(S3), 어떤 순서로 쓸지(S4)입니다.
- **S5는 두 가지로 구현할 수 있습니다.** 하나는 ⑥의 출력 안에 대조 결과를 적게 하는 것입니다(한계는 8.3). 다른 하나는 보고서의 날짜가 원문에 글자 그대로 있는지를 프로그램으로 확인하는 것입니다. 이 프로그램을 Skill의 스크립트로 넣었다면, 모델이 실행을 요청하고 앱이 돌립니다(8.2). 앱에 대조 단계를 따로 두었다면, 모델의 요청 없이 앱이 바로 합니다(그림의 점선). 어느 쪽이든 7.7에서 앱이 규칙으로 확인할 수 있는 것과 같은 종류입니다.

이 흐름에서 생성 모델은 두 번 실행되었고, 도구는 한 번 실행되었습니다. 도구 실행은 모델 실행이 아닙니다(1.4). 문서함에서 안내문을 먼저 찾아야 했다면 1.6처럼 검색 요청과 검색 실행이 한 번씩 더해졌을 것입니다. 이처럼 검색은 모델이 검색 도구를 요청하게 할 수도 있고, 5~7장처럼 앱이 정해진 순서로 먼저 해 둘 수도 있습니다. 어느 쪽인지는 앱의 구성에 따라 다릅니다. 7장 끝에서 말한 '남은 날 수 세기'도 이 흐름에 끼워 넣을 수 있습니다. 직원이 "마감까지 며칠 남았나"도 함께 물었다고 해 봅시다. 기준이 되는 오늘 날짜는 7.4처럼 앱이 입력에 넣습니다. 이때 Skill에 "남은 날 수는 날짜 계산 도구로 구한다"는 문장을 두면, ⑤와 ⑥ 사이에 날짜 계산 요청 출력, 앱의 도구 실행, 결과를 더해 다시 부르기가 한 번 더 들어갑니다. 그러면 생성 모델 실행은 세 번이 됩니다. 요청과 결과가 오가는 모습은 4.7에서 본 것과 같습니다.

> **이해 확인**
> 앱이 ⑤에서 처음 입력을 빼고 안내문 글만 모델에 보냈다면, ⑥의 보고서는 어떻게 달라질 수 있을까요?

## 8.5 Skill을 작성하면 무엇이 달라지는가

지금까지는 Skill이 출력을 '이렇게 이끌도록' 쓴 것이라고 설명했습니다. 실제로 그렇게 되는지는 실행해 보아야 압니다. 이 절에서는 같은 작업을 Skill 없이(실험 A), Skill을 넣고(실험 B) 실제로 실행해 출력을 비교합니다. 아래의 출력은 모두 실제 실행 결과이며, 편집하지 않았습니다.

### 8.5.1 비교 실험에서 같게 유지한 조건

Skill 말고 다른 조건이 다르면, 결과가 달라도 그 원인이 Skill인지 알 수 없습니다. 그래서 다음 조건을 같게 두었습니다.

| 비교 조건 | 이 실험에서 |
|---|---|
| 모델 | 두 실험 모두 Claude Sonnet 5.5(claude-sonnet-5-5) |
| 입력 자료 | 같은 교육 A 안내문 네 줄(1.6과 같음) |
| 사용자 요청 | 같은 문장 |
| 도구 | 두 실험 모두 도구 없음 |
| 대화 맥락 | 실행마다 새 대화. 앞선 대화 없음 |
| 앱의 지침 | 두 실험 모두 "당신은 회사 업무를 돕는 AI 어시스턴트입니다." 한 줄 |
| 유일한 차이 | 실험 B에만 안내 문장 한 줄("이번 작업에는 아래 Skill이 적용됩니다.")과 8.3의 Skill을 지침 뒤에 넣음 |
| 반복 | A와 B를 각각 3번 실행 |
| 같게 두지 못한 조건 | 온도는 실행 환경(이 실험에서 앱 역할을 한 실행 프로그램)에서 정할 수 없어 기본값을 썼습니다. 실행 환경이 입력에 자동으로 덧붙이는 내용(오늘 날짜 2026년 11월 3일 등)은 A와 B에 똑같이 들어갔습니다. |

처음 실행했을 때는 실행 환경이 이 책의 집필 메모를 입력에 자동으로 함께 넣고 있었습니다. 출력에 '교재'라는 말이 나와 이를 알게 되었고, 그 기능을 끈 뒤 처음부터 다시 실행했습니다. 사용자가 보지 못하는 입력이 출력에 영향을 줄 수 있다는 것(2.2)을 실험하는 쪽에서도 겪은 셈입니다. 대부분의 앱에서 사용자는 앱이 덧붙인 입력을 다 볼 수 없습니다. 같은 질문이라도 앱이 다르면 출력이 다를 수 있는 이유 가운데 하나입니다. 실행 방법과 버린 실행은 8.5.6 실행 기록에 적었습니다.

### 8.5.2 두 실험에 사용한 동일한 작업

두 실험의 사용자 입력은 다음과 같습니다. 요청 문장에는 실험 전에 정한 계획대로 출력 형식을 적지 않았습니다. 요청에 항목과 순서를 모두 적으면 Skill이 한 역할과 구분할 수 없기 때문입니다.

```text
[실제 입력] 실험 A·B의 사용자 입력 (같음)
[교육 안내문]
교육 A 신청 안내
- 교육일: 10월 8일
- 일반 신청 마감: 10월 5일
- 추가 모집 마감: 10월 7일 (지정 대상자에게만 적용)

이 교육 안내문을 검토해서 중요한 내용을 정리해 줘.
```

이 안내문에는 주의해서 읽지 않으면 놓치기 쉬운 조건(추가 모집은 지정 대상자에게만)이 있습니다. 또 신청 대상이 적혀 있지 않아서 S3이 작동하는지도 볼 수 있습니다. S2 가운데 '적용 대상 확인'은 이 안내문에서도 쓰입니다. 날짜가 세 개 있고 그 가운데 두 마감일의 대상이 다르기 때문입니다. 반면 '버전 확인'은 같은 항목의 날짜가 다른 문서가 없으므로 이 입력으로는 시험할 수 없습니다. Skill에는 이 안내문의 답(예: "일반 마감은 10월 5일")을 적지 않았습니다.

> - **대체 텍스트:** 왼쪽은 Skill 없이 실행한 출력으로, 핵심 일정 표, 주의할 점, 안내문에 없는 정보, 확인이 필요한 사항으로 이루어져 있고 일정 표의 비고에 '모든 신청자 대상'이라고 적혀 있다. 오른쪽은 Skill을 넣어 실행한 출력으로, 대상, 일정, 예외, 출처 순서의 보고서이며 일반 신청 대상을 확인 필요로 남기고 원문과 다시 대조한 결과를 적었다.
> - **성격:** 실제 실행 결과(2026년 11월 3일, Claude Sonnet 5.5). 출력은 편집하지 않았다.


### 8.5.4 결과를 판단한 기준

출력이 길거나 보기 좋다는 것만으로 Skill의 효과라고 하지 않습니다. 실험 전에 정해 둔 여섯 기준으로 여섯 개의 출력을 모두 채점했습니다. 칸의 숫자는 세 번 가운데 그 표시를 받은 횟수입니다.

| 평가 항목 | 확인한 내용 | 실험 A (3번) | 실험 B (3번) | 판단 근거 |
|---|---|---|---|---|
| 필수 정보 | 신청 대상, 마감일, 교육일을 다루었는가 | 충족 3 | 충족 3 | 모두 세 항목을 다루었다. 대상을 다룬 방식은 표 아래에 적었다. |
| 예외 구분 | 일반 조건과 예외 조건을 나누었는가 | 충족 3 | 충족 3 | 모두 10월 7일을 지정 대상자에게만 적용되는 날짜로 따로 적었다. |
| 근거 표시 | 내용이 원문의 어디서 왔는지 확인할 수 있는가 | 미충족 3 | 일부 충족 3 | A는 출처가 없다. B는 문서 이름을 밝혔지만, 7.5의 [1]처럼 문장마다 잇지는 않았다. |
| 추측 억제 | 자료에 없는 내용을 사실처럼 더하지 않았는가 | 일부 충족 3 | 충족 2, 일부 충족 1 | A는 세 번 모두 한 가지씩, B는 한 번 더했다(표 아래). |
| 결과 형식 | 필요한 항목을 빨리 찾을 수 있는가 | 충족 3 | 충족 3 | 모두 표와 제목으로 정리했다. 순서는 B만 세 번 같았다. |
| 검증 흔적 | 날짜와 대상 조건을 다시 대조한 흔적이 있는가 | 미충족 3 | 충족 3 | 대조 결과 문장이 있는지만 셌다. B는 세 번 모두 있었다. |

표의 근거를 조금 더 적으면 다음과 같습니다.

- **대상을 다룬 방식(필수 정보, 추측 억제):** A-1은 대상을 '안내문에 빠져 있는 정보'에 넣었습니다. A-2도 '확인이 필요한 부분'에 넣었지만, 같은 출력의 일정 표에는 대상을 '전체'라고 적었습니다. A-3은 '모든 신청자 대상'이라고 적었습니다. B는 세 번 모두 일반 신청 대상을 '확인 필요'로 남겼지만, B-1은 일정 표의 비고에 '전체 대상'이라고도 적었습니다.
- **A-1의 또 다른 추측:** 추가 모집이 "일반 마감 이후 2일간만 열리며"라고 적었습니다. 안내문에는 추가 모집이 언제 시작하는지 없습니다.
- **결과 형식:** A는 실행마다 제목과 구성이 조금씩 달랐고, B는 세 번 모두 대상·일정·예외·출처 순서였습니다.

S2는 둘로 나누어 보았습니다. '적용 대상 확인'은 작동한 것으로 보입니다. B는 세 번 모두 두 마감일이 대상이 달라 충돌이 아니라는 문장을 적었습니다. 대상을 나눈 것은 A도 세 번 모두 했지만, '충돌이 아니다'라고 따로 적은 것은 B의 세 번뿐입니다. 7.6에서 본 '적용 대상이 다르면 충돌이 아니다'와 같은 내용입니다. '버전 확인'은 시험할 자료가 없어 평가하지 않았습니다.

### 8.5.5 결과를 해석할 때 주의할 점

**차이는 생각보다 작은 곳에서 나타났습니다.** Skill이 없어도 예외 조건을 구분한 출력이 나왔습니다. Skill이 바꾼 것은 주로 출력의 순서, 출처 표시, 신청 대상을 추측하지 않고 '확인 필요'로 남긴 것, 대조 결과 문장이었습니다. 차이를 크게 보이게 하려고 요청이나 결과를 바꾸지 않았습니다. 다른 모델이나 더 복잡한 안내문이라면 차이가 다르게 나올 수 있습니다.

**Skill이 정확성을 보장하지는 않습니다.** Skill에 "추측하지 않는다"고 적었는데도 실험 B 세 번 가운데 한 번은 일반 신청 대상을 '전체 대상'이라고 적었습니다. Skill은 출력의 방향을 이끄는 입력일 뿐이므로, 한 번 잘 나온 결과만 보고 판단하지 않고 여러 번 실행해 보아야 합니다. 대조 결과 문장도 출력이라는 점(8.3)은 아래 이해 확인에서 다시 묻습니다.

**Skill은 모델을 바꾸지 않았습니다.** 두 실험은 같은 모델로 실행했고, 실험 B가 달랐던 것은 입력에 Skill의 문장이 더 있었기 때문입니다(1.5, 4.9). 실험 B의 입력은 실험 A보다 약 240토큰 길었는데, 그 차이가 안내 문장 한 줄과 Skill의 분량입니다.

**여섯 출력 모두 연도나 회차를 확인하라고 적었습니다.** 실행 환경이 오늘 날짜(2026년 11월 3일)를 입력에 넣었기 때문에, 출력은 모두 "10월 일정이 이미 지났을 수 있다"는 취지로 연도나 다음 회차를 확인하라고 적었습니다. 7.4에서 앱이 오늘 날짜를 입력에 넣은 것과 같은 일이 실험에서도 일어난 것입니다. 이 문장은 A와 B에 똑같이 나왔으므로 Skill의 효과가 아닙니다.

> **이해 확인**
> 실험 B의 출력에 "원문과 다시 대조했고 일치합니다"라는 문장이 있습니다. 이 문장만 보고 "Skill 덕분에 날짜가 검증되었다"고 말해도 될까요?

## 스스로 확인하기

1. Skill의 설명(description)에는 무엇을 적어야 하고, 그것이 왜 중요한가요?
2. 8.4의 흐름에서 생성 모델은 몇 번 실행되었고, 파일을 실제로 연 것은 무엇인가요?
3. 8.5에서 Skill이 있을 때와 없을 때 출력에 생긴 차이를 두 가지 들어 보세요. 반대로 Skill이 없어도 이미 되던 것은 무엇이었나요?
4. 8.5의 실험에서 '같게 두지 못한 조건'은 무엇이었고, 그것이 A와 B의 비교를 망치지 않은 이유는 무엇인가요?

## 이해 확인 해설

본문 중간의 '이해 확인'과 위의 '스스로 확인하기'에 대한 짧은 해설입니다. 먼저 스스로 답해 본 뒤 비교해 보세요.

**본문 중간의 이해 확인**

- **8.1 Skill 스무 개** — 들어가지 않습니다. 처음에는 스무 개의 이름과 설명만 들어가고, 요청과 설명이 맞는 Skill의 본문만 입력에 더해집니다. 입력 길이를 아끼기 위해서입니다.
- **8.2 도구가 연결되어 있지 않을 때** — 열리지 않습니다. Skill은 무엇을 할지 안내할 뿐이고, 파일을 여는 것은 앱이 연결한 도구입니다(1.5의 "Skill은 방향을 알려 주고, 도구는 손을 움직입니다"). 모델이 파일 읽기 요청을 출력하더라도 실행할 도구가 없습니다.
- **8.3 S2를 "10월 5일을 쓴다"로 바꾸면** — Skill에 이 안내문의 답을 적은 셈이 됩니다. 다른 교육의 안내문이나 날짜가 바뀐 새 안내문에는 맞지 않는 규칙이 되고, 지정 대상자처럼 10월 7일이 맞는 경우도 틀리게 만듭니다. Skill에는 확인하는 절차를 적어야 합니다.
- **8.4 ⑤에서 처음 입력을 뺀다면** — 두 번째 실행의 입력에는 Skill도 사용자의 요청도 없게 됩니다. 모델은 앞선 실행을 스스로 기억하지 못하므로(1.6, 4.7), 보고서의 순서나 '확인 필요' 표시 같은 Skill의 영향이 사라지고, 무엇을 해 달라는지도 입력에 없으므로, 안내문을 그냥 요약하는 등 엉뚱한 출력이 나올 수 있습니다.
- **8.5 "대조했고 일치합니다"** — 그렇게 말할 수 없습니다. 그 문장은 S5가 이끈 출력의 한 부분이고, 실제로 대조가 이루어졌다는 증거는 아닙니다(4.8). 이 경우에는 원문 네 줄과 보고서를 사람이 직접 맞춰 보면 날짜가 일치하지만, 그것은 우리가 확인한 결과입니다. 검증을 보장하려면 앱이 프로그램으로 대조하거나 사람이 확인해야 합니다(8.4, 7.7).

**스스로 확인하기**

1. 무엇을 하는 Skill인지와 언제 쓰는지를 적습니다. 처음에는 이름과 설명만 입력에 들어가므로, 설명이 분명해야 앱이 요청에 맞는 Skill을 골라 본문을 넣을 수 있습니다.
2. 두 번입니다(파일 읽기 요청 출력, 보고서 출력). 파일을 실제로 연 것은 앱이 실행한 파일 읽기 도구이며, 도구 실행은 모델 실행으로 세지 않습니다.
3. 차이는 항목 순서(대상·일정·예외·출처로 고정), 출처 표시, 신청 대상을 추측하지 않고 '확인 필요'로 남긴 것, 대조 결과 문장 가운데 두 가지를 들면 됩니다. Skill이 없어도 이미 되던 것은 추가 모집이 지정 대상자에게만 적용된다는 예외 조건의 구분입니다.
4. 온도를 정할 수 없었고, 실행 환경이 오늘 날짜 같은 내용을 입력에 덧붙였습니다. 두 조건 모두 A와 B에 똑같이 적용되었으므로, A와 B의 차이를 Skill 말고 다른 것 탓으로 돌릴 이유가 되지 않습니다. 다만 그 영향(예: 연도 확인 문장)은 A와 B에 똑같이 나타났습니다.

## 다음 장으로

8.5에서 Skill은 모델을 바꾸지 않고 입력만 바꾸었습니다. 그래서 Skill을 빼면 출력도 Skill 없는 모양으로 돌아갑니다. 그렇다면 대상·일정·예외·출처 순서의 보고서 형식을 Skill 없이도 늘 지키게 하려면, 모델 자체를 바꾸어야 할까요? 9장에서는 입력에 지침을 넣는 것과 모델을 추가로 학습시키는 Fine tuning이 무엇을 바꾸는지 구분해 봅니다.
