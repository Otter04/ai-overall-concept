## 부록 A 핵심 용어 찾아보기

이 책에서 굵은 글씨로 설명한 용어 가운데, 장의 흐름을 따라가는 데 꼭 필요하거나 다른 장에서 다시 쓰이는 것을 골랐습니다. 장 순서로 늘어놓았고, 처음 설명한 절을 함께 적었습니다. 더 자세한 설명은 그 절에 있습니다.

### 1장

| 용어 | 처음 설명한 절 | 뜻 |
|---|---|---|
| 앱 | 1.2 | 사용자가 만나는 화면과, 그 뒤에서 정보를 처리하고 모델과 도구를 연결하는 부분까지 합친 것입니다. 스마트폰 어플, 웹 서비스, 컴퓨터 프로그램을 모두 포함합니다. |
| 모델 | 1.3 | 입력을 받아 출력을 만들어 내는 프로그램입니다. 이 책에서는 주로 글을 받아 글을 만드는 언어 모델을 다룹니다. |
| 도구 | 1.4 | 검색, 계산, 파일 읽기처럼 구체적인 기능 하나를 실제로 실행하는 프로그램입니다. 모델이 출력한 요청을 받아 앱이 실행합니다. |
| Skill | 1.5 | 특정 작업을 위한 절차, 기준, 참고자료, 결과물 형식, 검증 방법을 묶어 둔 작업 안내서입니다. 앱이 입력에 넣을 뿐 모델 자체를 바꾸지는 않습니다. |

### 2장

| 용어 | 처음 설명한 절 | 뜻 |
|---|---|---|
| 토큰화 | 2.1 | 입력 문장을 토큰으로 나누고, 각 토큰을 번호(토큰 ID)로 바꾸는 단계입니다. |
| 토큰 | 2.1 | 모델이 글을 다루는 작은 조각입니다. 단어 하나일 수도 있고 단어의 일부일 수도 있습니다. |
| 토큰 ID | 2.3 | 어휘 사전의 각 토큰에 붙은 고유한 번호입니다. 번호가 가깝다고 뜻이 가까운 것은 아닙니다. |
| 임베딩 | 2.1 | 토큰 번호를 계산에 쓸 수 있는 숫자 묶음으로 바꾸는 단계입니다. 5장과 6장의 검색용 임베딩과는 다릅니다(5.5). |
| 파라미터 | 2.1 | 학습으로 정해진 모델 안의 수많은 숫자입니다. 질문하는 동안에는 바뀌지 않고, 학습할 때만 바뀝니다. |
| 컨텍스트 | 2.2 | 이번 실행에서 모델이 참고하도록 함께 전달되는 정보 전체입니다. 질문, 앱의 지침, 대화 기록, 찾아 온 자료 등이 들어갑니다. |
| 컨텍스트 윈도 | 2.2 | 모델이 한 번에 받아들일 수 있는 입력 길이의 한계입니다. 글자 수가 아니라 토큰 수로 셉니다. |
| 벡터 | 2.4 | 여러 숫자를 한 줄로 묶은 것입니다. 이 책에서는 '숫자 묶음'이라고도 부릅니다. |
| Transformer | 2.5 | 오늘날 대부분의 텍스트 생성 모델이 바탕으로 삼는 구조입니다. 특정 모델의 이름이 아니라, 레이어를 구성하고 쌓는 설계 방식입니다. |
| Attention | 2.5 | 각 토큰의 숫자 묶음에, 관계가 깊은 다른 토큰의 정보를 가져와 섞는 계산입니다. 3장에서 자세히 다룹니다. |
| 로짓 | 2.6 | 마지막 레이어의 계산 결과로 어휘 사전의 모든 토큰에 하나씩 매기는 점수입니다. |
| 소프트맥스 | 2.6 | 로짓을 0과 1 사이의 값으로 바꾸고 합이 1이 되게 맞춰, 다음 토큰의 확률로 읽을 수 있게 하는 계산입니다. |
| Temperature | 2.6 | 토큰 확률의 차이를 얼마나 벌리거나 좁힐지 정하는 설정입니다. 낮추면 같은 토큰이 뽑히기 쉽고, 높이면 다양한 토큰이 뽑힐 가능성이 커집니다. |
| Top-k | 2.6 | 확률이 높은 순서로 k개 후보만 남기고 그 안에서 다음 토큰을 뽑는 설정입니다. 6.6의 검색 Top-k와는 이름만 같습니다. |

### 3장

| 용어 | 처음 설명한 절 | 뜻 |
|---|---|---|
| Q, K, V | 3.3 | Attention 계산에서 각 토큰이 자기 숫자 묶음으로 만드는 세 숫자 묶음입니다. Q는 관계를 계산하려고 내미는 것, K는 비교 대상이 될 때 내미는 것, V는 실제로 건네질 정보입니다. |

### 4장

### 2.8에서 다룬 용어

2.8은 읽지 않아도 되는 절입니다. 기사나 제품 설명에서 이 용어들을 만났을 때 찾아볼 수 있도록 따로 묶었습니다.

| 용어 | 처음 설명한 절 | 뜻 |
|---|---|---|
| Top-p | 2.8 | 확률이 높은 후보부터 차례로 더해 가다가, 합이 p에 이를 때까지의 후보만 남기는 설정입니다. |
| 자기회귀 | 2.8 | 앞에서 만든 토큰을 다음 차례의 입력에 붙여 하나씩 이어 가는 생성 방식입니다. |
| 스트리밍 | 2.8 | 결과를 만들어지는 대로 조금씩 전달하는 방식입니다. 답변이 조금씩 화면에 나타나는 것이 이 방식입니다. |
| Prefill | 2.8 | 처음 들어온 컨텍스트 전체를 한꺼번에 계산하는 구간입니다. 첫 글자가 나오기까지 기다리는 시간이 이 구간입니다. |
| Decode | 2.8 | Prefill 다음부터 토큰을 하나씩 만들어 가는 구간입니다. |
| KV 캐시 | 2.8 | 앞쪽 토큰들에 대해 이미 계산한 결과를 메모해 두었다가 다시 쓰는 것입니다. 계산을 빠르게 해 줄 뿐, 결과를 바꾸지는 않습니다. |

> - **구성 요소:** 세 줄. 첫째 줄 '문서가 생기거나 바뀔 때': 원본 문서 → 추출 → 청크·메타데이터 → 임베딩 → Vector DB·키워드 색인. 둘째 줄 '질문 전, 한 번': 학습 예시 → 사전학습·후속학습·Fine tuning → 조정된 모델. 셋째 줄 '질문마다': 질문 → 앱(입력 구성) → 검색 → 근거 선택 → 모델 Inference(Skill·도구 포함) → 확인 → 답변. 첫째 줄의 색인과 둘째 줄의 모델에서 셋째 줄로 내려오는 점선 화살표.
> - **배치와 흐름:** 위아래 세 줄을 회색 구분선으로 나누고, 줄마다 왼쪽에 언제 일어나는지를 적는다. 셋째 줄만 굵은 테두리.
> - **디자인 메모(시안, 확정 아님):** 이 장과 책 전체의 대표 그림 후보다. 그림 9-1의 두 줄에 맨 위 줄을 더한 모양이며, 5장의 준비 그림과 같은 단계 이름을 쓴다.
> - **대체 텍스트:** 세 줄로 나뉜 그림. 맨 위 줄은 문서가 생기거나 바뀔 때 일어나는 자료 준비로, 원본 문서가 추출, 청크와 메타데이터, 임베딩을 거쳐 색인이 된다. 가운데 줄은 질문 전에 한 번 일어나는 모델 학습으로, 학습 예시가 학습을 거쳐 조정된 모델이 된다. 아래 줄은 질문마다 일어나는 답하기로, 질문이 입력 구성, 검색, 근거 선택, 모델의 Inference, 확인을 거쳐 답변이 된다. 위의 두 줄에서 아래 줄로 점선 화살표가 내려온다.

## 부록 C 이해 확인 질문 모음

이름이나 모양이 비슷해 헷갈리기 쉬운 개념을 둘씩 묶어 구분하는 질문입니다. 본문의 이해 확인과는 겹치지 않게 골랐습니다. 먼저 자기 말로 답해 본 뒤 답을 펼쳐 보세요.

**1. 두 가지 임베딩**

2.4의 임베딩과 5.5의 검색용 임베딩은 둘 다 무언가를 숫자 묶음으로 바꿉니다. 무엇을 바꾸는지와 어디에서 일어나는지로 둘을 구분해 보세요.

> **답**
> 2.4의 임베딩은 토큰 하나를 숫자 묶음으로 바꾸는 단계이고, 생성 모델 안의 첫 단계입니다. 5.5의 검색용 임베딩은 청크나 질문 같은 글 전체를 벡터 하나로 바꾸는 일이고, 생성 모델과는 다른 검색용 임베딩 모델이 합니다. 앞의 것은 답변을 만드는 계산의 재료이고, 뒤의 것은 자료를 찾기 위한 재료입니다(5.5의 표).

**2. 두 가지 Top-k**

2.6의 Top-k를 5로 정하는 것과 6.6의 검색 Top-k를 5로 정하는 것은 각각 무엇을 바꿀까요?

> **답**
> 2.6의 Top-k는 다음 토큰을 뽑을 때 확률이 높은 토큰 5개 안에서만 뽑게 합니다. 답변에 들어갈 토큰을 고르는 설정입니다. 6.6의 검색 Top-k는 검색 결과 가운데 상위 5개 조각만 다음 단계로 넘기게 합니다. 모델의 입력에 들어갈 수 있는 자료의 수를 정하는 설정입니다. 이름만 같고 쓰이는 곳이 다릅니다.

**3. Attention의 비교와 의미 기반 검색의 비교**

Attention과 의미 기반 검색은 둘 다 숫자 묶음을 비교하고, 그 비교에 내적을 쓸 수 있습니다. 무엇과 무엇을 비교하는지, 그 비교가 무엇을 위한 것인지로 구분해 보세요.

> **답**
> Attention은 모델 안에서, 이미 입력에 들어온 토큰끼리 비교해 정보를 섞습니다(3.4). 의미 기반 검색은 모델을 실행하기 전에, 질문 벡터와 저장해 둔 청크 벡터를 비교해 무엇을 입력에 넣을지 고릅니다(6.5). 앞의 것은 입력 안에서 일어나는 계산이고, 뒤의 것은 입력을 만들기 위한 비교입니다.

**4. Reasoning과 '추론 모델'**

"'추론 모델'만 Reasoning을 하고, 다른 모델은 Reasoning을 하지 않는다." 이 말을 바르게 고쳐 보세요.

> **답**
> Reasoning은 입력 안의 조건과 정보를 연결해 결론을 얻는 문제 해결입니다. 문제가 조건을 이어야 풀리는 것이라면, 어떤 생성 모델이든 그 Inference 안에서 Reasoning이 함께 이루어집니다(4.1, 4.5). 추론 모델이 다른 점은 최종 답 전에 풀이를 먼저 길게 출력하도록 학습되었다는 것입니다. 출력한 중간 결과가 다음 토큰을 고를 때의 입력으로 쌓이므로, 단계가 많은 문제에서 조건을 차례로 잇는 데 도움이 될 수 있습니다(4.8).

**5. 점수를 더하기와 순위로 합치기**

BM25 점수와 코사인 유사도는 둘 다 높을수록 질문과 잘 맞는다는 뜻입니다. 그런데 6.8에서는 두 점수를 더하지 않고 순위로 합쳤습니다. 왜 그럴까요?

> **답**
> 두 점수는 범위와 뜻이 다릅니다. BM25 점수는 단어 통계로 계산하며 검색어가 길어지면 더 커질 수 있고, 코사인 유사도는 두 벡터의 방향이 같은 정도입니다. 그대로 더하면 서로 다른 잣대의 값을 같은 잣대인 것처럼 섞게 됩니다. 1위, 2위 같은 순위는 어느 검색에서 왔든 같은 뜻을 가지므로, RRF는 순위만 보고 두 목록을 합칩니다(6.8).

**6. 재정렬 모델과 생성 모델**

재정렬 모델과 생성 모델은 둘 다 모델이고, 실행하면 Inference입니다. 무엇을 입력받아 무엇을 출력하는지로 둘을 구분해 보세요.

> **답**
> 재정렬 모델은 질문과 후보 조각 하나를 한꺼번에 입력받아, 그 조각이 질문과 얼마나 관련 있는지를 나타내는 점수 하나를 출력합니다(6.10). 생성 모델은 질문, 앱의 지침, 고른 근거가 담긴 컨텍스트를 입력받아 토큰을 하나씩 골라 이어 붙인 글을 출력합니다(2장, 7.5). 재정렬 모델의 점수는 입력에 넣을 자료의 순서를 정하는 데 쓰이고, 답변 글은 생성 모델이 만듭니다.

**7. RAG와 Skill**

RAG와 Skill은 둘 다 앱이 모델의 입력에 무언가를 더하는 방식입니다. 무엇을 더하는지와, 그것이 답변의 어느 쪽을 바꾸는지로 구분해 보세요.

> **답**
> RAG는 질문과 관련된 자료를 검색으로 찾아 근거로 넣습니다(5.1, 7.4). 그래서 답변이 무엇을 근거로 삼는지가 바뀝니다. Skill은 그 작업의 절차, 기준, 결과물 형식을 적은 안내서를 넣습니다(1.5, 8.1). 그래서 어떤 순서와 기준으로 답변을 쓰는지가 바뀝니다. 둘 다 입력을 바꿀 뿐 모델의 파라미터는 바꾸지 않습니다.

**8. Skill과 Fine tuning**

보고서를 늘 대상, 일정, 예외, 출처 순서로 쓰게 하고 싶습니다. Skill로 하는 방법과 Fine tuning으로 하는 방법은 무엇이 바뀌고, 그 일이 언제 일어나는지가 어떻게 다를까요?

> **답**
> Skill은 이번 실행의 입력을 바꿉니다. 요청이 들어올 때마다 앱이 Skill을 입력에 넣고, 빼면 다음 실행부터 원래대로 돌아갑니다. Fine tuning은 모델의 파라미터를 바꿉니다. 질문을 받기 전에 한 번 학습해 두고, 질문에는 학습이 끝난 모델로 Inference만 합니다(9.1의 표). 어느 쪽이든 출력이 정말 그 순서를 지켰는지는 따로 확인해야 합니다(8.5, 9.8).

**9. 학습 중의 순전파와 질문에 답할 때의 Inference**

9.5.2는 순전파가 'Inference의 계산과 같은 길'이라고 했습니다. 그렇다면 Fine tuning 중의 순전파와, 질문에 답할 때의 Inference는 무엇이 다를까요?

> **답**
> 입력이 레이어를 지나 다음 토큰의 확률이 나오기까지는 같습니다. 다른 것은 그다음입니다. 학습에서는 그 예측을 목표 응답과 비교해 손실을 구하고, 역전파로 기울기를 얻어 파라미터를 갱신합니다(9.5). 질문에 답할 때는 확률에서 다음 토큰을 골라 출력을 이어 갈 뿐, 손실을 구하지 않고 파라미터도 바뀌지 않습니다(2.6, 9.1).

**10. 환각과 입력에 있던 틀린 날짜**

10.7의 잘못된 답은 일반 신청 마감을 10월 4일이라고 했습니다. 이 답을 환각이라고 부르면 왜 원인을 찾기 어려워질까요?

> **답**
> 10월 4일은 모델이 지어낸 날짜가 아니라, 입력에 들어 있던 지난해 안내의 날짜입니다(10.7). 본문에서 환각의 예로 든 것은 입력 어디에도 없던 날짜와 서류를 그럴듯하게 채운 출력이었습니다(9.3, 10.2.1). 이 답을 같은 이름으로 부르면 모델이 지어낸 것으로 보고 모델의 출력만 들여다보게 됩니다. 이 경우에는 무엇이 입력에 들어갔고 무엇이 빠졌는지를 먼저 보고, 그 자료가 어떻게 골라졌는지 검색 결과 정리와 자료 준비 단계까지 거슬러 올라가야 원인이 드러납니다(그림 10-6).

## 부록 D LoRA 미리보기

9.7에서 Fine tuning에는 두 가지 방향이 있다고 했습니다. 기존 모델의 많은 파라미터를 직접 고치는 전체 Fine tuning과, 원래 파라미터는 그대로 두고 적은 수의 파라미터만 학습하는 효율적인 방법입니다. **LoRA**는 뒤쪽 방법 가운데 널리 쓰이는 것으로, 이름은 Low-Rank Adaptation의 머리글자입니다. 이 부록에서는 LoRA가 전체 Fine tuning과 어떤 방향이 다른지, 왜 쓰는지만 정리합니다.

### 무엇을 학습하는가

LoRA는 원래 모델의 파라미터를 고치지 않습니다. 대신 원래 파라미터 곁에 적은 수의 파라미터를 새로 더하고, 학습으로는 이 더한 파라미터만 바꿉니다. 9.5의 순서로 보면 순전파, 손실, 역전파는 같은 순서로 일어나고, 마지막의 파라미터 갱신이 더한 파라미터에만 일어납니다.

| 구분 | 전체 Fine tuning | LoRA |
|---|---|---|
| 학습으로 바뀌는 것 | 기존 모델의 많은 파라미터 | 새로 더한 적은 수의 파라미터. 원래 파라미터는 그대로 둔다 |
| 학습 뒤에 보관할 것 | 학습이 끝난 모델 전체 | 더한 파라미터만 |
| 목적이 여러 개일 때 | 목적마다 모델 전체를 하나씩 보관한다 | 원래 모델 하나에, 목적별로 더한 파라미터만 따로 보관한다 |
| 질문에 답할 때 쓰는 것 | 학습이 끝난 모델 | 원래 모델과, 그 목적에 맞게 더한 파라미터를 함께 |

### 왜 쓰는가

학습할 파라미터가 적으면 학습에 드는 계산 자원이 줄고, 학습 뒤에 보관할 것도 적어집니다(9.7). 교육 안내문 보고서용, 회의록 요약용, 문의 분류용처럼 목적이 다른 Fine tuning을 세 개 한다고 해 봅시다. 전체 Fine tuning이라면 학습이 끝난 모델 세 개를 모두 보관해야 합니다. LoRA라면 원래 모델 하나와, 목적별로 더한 작은 파라미터 묶음 세 개만 두면 됩니다. 질문에 답할 때는 그 목적에 맞는 묶음을 원래 모델과 함께 씁니다. 원래 파라미터가 그대로 남아 있으므로, 더한 묶음을 쓰지 않으면 원래 모델 그대로 답하게 됩니다.

### 바뀌지 않는 것

LoRA도 Fine tuning입니다. 9장에서 본 구분은 그대로 적용됩니다.

- 학습은 질문을 받기 전에 끝내 두고, 질문에는 Inference만 합니다(9.1).
- 자주 바뀌는 마감일이나 규정을 답에 반영하는 데는 여전히 RAG가 알맞습니다(9.3).
- 학습이 끝난 뒤에는 원하는 형식과 행동이 실제로 나오는지 평가해야 합니다(9.8).

### 2편에서 다룰 것

더한 파라미터가 어떤 모양이고 왜 적은 수로도 충분한지(이름의 Low-Rank가 가리키는 내용), 학습할 때 정하는 설정값, 직접 해 보는 실습은 이 책의 다음 편(2편)에서 다룹니다.
